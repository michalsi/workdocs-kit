# Workdocs conventions

Canonical spec for the workdocs content root (default `~/workdocs`). Agents: read this before creating, restructuring, or closing anything there. Skills and templates defer to this file; where they disagree, this file wins.

## Hard rules

1. Personal project and task material never lives in a code repo working tree. Exception: files a repo's own tooling writes (for example a test harness's `reports/`), and docs the code itself needs (runbooks, harness READMEs). Reference those; do not copy them.
2. Status lives in exactly one file per project: `HANDOFF.md`.
3. `LOG.md` is append-only, newest entry first. Never edit an old entry except to correct a factual error. A failed attempt keeps its own entry; a later success does not replace it.
4. Numbered files are numbered in creation order and are never renumbered or reused.
5. Absolute dates only (`YYYY-MM-DD`). Get today's date with `date +%F`; never infer it.
6. No spaces in file or directory names. `-` inside words, `_` between structural parts of a name.
7. No hard-wrapped prose in new writing: one paragraph, list item, or table row per line.
8. Never delete. Supersede, mark `status: done`, or move to an `archive/` folder.
9. Bulky or raw material (CI downloads, raw logs, recovered sessions, anything over about 1 MB or 50 files) goes to `data/`, never into the docs tree.
10. A new top-level folder in the content root is a decision for the user, not the agent.

## Layout

```text
~/workdocs/
├── README.md            pointer to this file + machine-specific notes
├── INDEX.md             generated by `wd index`; do not edit by hand
├── projects/
│   ├── <epic>/          kind: epic   (README, HANDOFF, LOG, DECISIONS, sub-projects)
│   │   └── <project>/   kind: project
│   └── <project>/       kind: project (top level when it has no epic)
├── reviews/             single-file reviews of other people's PRs
├── notes/               single-file one-off analyses
├── archive/             bulk dumps from migrations, unchanged
└── data/                git-ignored; data/<unit path under projects>/…
```

Nesting stops at epic → project. Work below a project is a task card under `tasks/`. An epic may also be a phase group without its own Jira ticket (for example `phase-2` covering several tickets); the `jira` list then carries every key in the group.

## Unit kinds

| Kind | Shape | Use when |
|---|---|---|
| `note` | `notes/<KEY-or-slug>_<YYYYMMDD>[_<kebab>].md` | one sitting, one output, no follow-up expected |
| `review` | `reviews/<KEY>_<YYYYMMDD>[_<kebab>].md` | review of someone else's PR; later iterations are appended as dated `##` sections in the same file |
| `project` | directory with the file contract | work spans sessions, has a next action, or needs more than one file |
| `epic` | directory with the file contract plus sub-project directories | several projects share background, decisions, or a Jira epic or phase |

A note or review graduates to a project as soon as it needs a second file or continues into another session: `wd promote <file>`. Reviews of a project's own PRs go in that project's `reviews/`.

## Project file contract

| File | Role | Write mode |
|---|---|---|
| `README.md` | frontmatter; objective, scope, out of scope, glossary, map of numbered docs | edit; changes rarely |
| `HANDOFF.md` | current state: status, next action, blockers, authorization, read order, task table, project rules | overwrite sections every working session |
| `LOG.md` | dated history: what was done, found, changed | append only, newest first |
| `DECISIONS.md` | `D1…` entries: date, decision, reason, where it was agreed | append; created on first decision; superseded entries are marked, not removed |
| `NN-<kebab>.md` | content: background, analysis, plans, audits, reports | edit until superseded |
| `NN-<kebab>/` | a group of imported or related content files | as above |
| `tasks/TNN-<kebab>/HANDOFF.md` | a bounded sub-task a separate agent can run alone | as HANDOFF |
| `reviews/YYYYMMDD-<kebab>/` | grill outputs, plan reviews, reviews of this project's own PRs | write once |
| `scripts/`, `outputs/` | analysis code; small derived results (under about 1 MB) | free |
| `archive/` | superseded material kept for history | move in, never edit |

The two-week test decides where a statement goes: if it would be wrong in two weeks, it is dated evidence (LOG or a numbered doc). If it must stay true, it belongs in README, HANDOFF, or DECISIONS.

Reading order is set by HANDOFF's "Read first" list, not by file numbers. A replaced numbered doc stays in place with one line at the top: `> Superseded by [07-revised-matrix.md](07-revised-matrix.md) on 2026-09-14.`

Large projects may keep a numbered backlog or tracker doc for detail (dependency graphs, milestone gates). Task status is still kept only in HANDOFF's task table.

## Frontmatter

Only in `README.md` of epics and projects, and at the top of single-file notes and reviews. Only these keys:

```yaml
---
kind: project            # epic | project | review | note
title: Human-readable title
status: active           # active | waiting | paused | done
jira: [PROJ-1, PROJ-2]   # every key the unit answers to; first is primary; [] if none
repos: [webapp]          # repo identity = origin URL basename, not the checkout dir
branches: [feature/PROJ-1-x]   # exact branch names; never trunk branches (main, stage, …)
waiting_on: []           # required with status: waiting
ping_after:              # required with status: waiting (YYYY-MM-DD)
created: 2026-10-02
---
```

Values are scalars or flow lists `[a, b]`; `wd` parses nothing else. There is no `updated` key: the newest LOG heading and git history provide it.

## Naming and references

- Project directories: `<PRIMARY-JIRA-KEY>-<kebab-slug>`, or `<slug>` when there is no single ticket (phase groups, tooling work).
- Links between workdocs files: relative markdown links. Links from workdocs into `data/`: `data/<path>` relative to the content root, written as code, not as a link.
- Code references are repo-qualified, never checkout-qualified: `webapp:src/billing/invoice.ts:109@ecd35657`. The agent maps `webapp:` to whichever checkout it runs in, so checkouts `webapp-1` and `webapp-2` of the same origin are both `webapp`.
- CI builds, tickets, dashboards: full URLs.

## HANDOFF.md shape

```markdown
# Handoff: <title>

## Status (YYYY-MM-DD)
Two or three sentences: what is true now.

## Next action
1. Concrete enough to start without asking.

## Blocked / waiting
- <what> — waiting on <who> since <date>, chase <date>

## Authorization
- Allowed: …
- Not allowed without explicit approval: …

## Read first
1. README.md
2. …

## Tasks
| Task | Status | Depends on | Card |
|---|---|---|---|

## Project rules
- Invariants every agent on this project must respect.
```

Omit sections that are empty, except Status and Next action.

## LOG.md entry shape

```markdown
## YYYY-MM-DD — <agent or person> (<checkout or context>) — <one-line summary>

- Done: …
- Found: …
- Evidence: links to outputs/, data/ paths, CI URLs
- Docs changed: HANDOFF (status, next action), 03 (coverage table)
- Commits: <repo>@<sha> on <branch>
```

Leave out bullets that do not apply. Several entries on one date are fine.

## Finding the project for the current work

Run `wd where`. It matches, in this priority order:

1. an explicit term (`wd where PROJ-1234` or `wd where phase-2`);
2. the exact current branch listed in `branches`;
3. a Jira key in the branch name listed in `jira`;
4. the repo listed in `repos`, only when nothing above matched and exactly one unit lists that repo.

A project outranks its own epic. On one match, use it. On none or several, ask the user once. Then either `wd new …` or `wd link <unit>` records the mapping so the question does not repeat.

## When to write

Write as work happens, not at the end of a session: sessions get closed, interrupted, or compacted without warning. Append a LOG entry, and update HANDOFF when status or next action changed, right after any of:

- a finding verified or a hypothesis ruled out;
- a decision made, or approved by the user;
- a run or build started, finished, or failed (record the URL either way);
- the plan, scope, or next action changed;
- before asking the user to wait for something or to decide something.

Claude Code backs this up with hooks: the Stop hook blocks once when about 20 tool calls (`NUDGE_AFTER`) have passed in a workdocs project without a LOG/HANDOFF write, and the session-start hook adds a reminder right after a context compaction. Other agents rely on this section alone.

## Agent completion protocol

Before ending a session that changed a project's state (in addition to the writes above):

1. Update HANDOFF: Status (with today's date), Next action, Blocked, Tasks.
2. Append a LOG entry.
3. If a numbered doc was added, add it to the README document map.
4. If a decision was made, add it to DECISIONS.
5. `wd checkpoint -m "<unit>: <summary>"`.

Say plainly which workdocs files were created or edited.

## Migrating loose files out of a repo

1. `wd audit` lists untracked files per checkout.
2. Propose a mapping (file → unit) and get the user's approval per checkout before moving anything. Untracked code stays in the repo unless explicitly approved.
3. Move with `mv` (same filesystem, atomic). Bulky material goes to `data/`.
4. Rewrite references to the old paths inside the moved docs. Run `wd lint`.
5. `wd checkpoint` after each checkout.
